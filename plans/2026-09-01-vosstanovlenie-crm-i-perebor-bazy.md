## Контекст

CRM не использовалась с 9 июня 2026 (последнее касание прод-базы). Дмитрий:
«неудобно заполнять, накопились сотни клиентов, поэтому не пользовался».

Разбор 2026-09-01 показал, что дело **не в удобстве ввода**, а в том, что
инструмент не звал обратно: `next_action_due` пуст у всех лидов → страница
«Сегодня» пустая → возвращаться некуда.

**Ключевое решение:** голосовой ввод в CRM **не строим**. Роль голосового
интерфейса выполняет агент в чате Claude Code — Дмитрий диктует, агент пишет
напрямую в прод-базу Turso и показывает результат. Если через практику выяснится,
что не хватает мобильности (ввод с телефона) — тогда вернёмся к Telegram-боту
из `2026-05-19-mvp-fase-2-telegram-snooze.md`.

**Новый этап:** помимо аренды помещений появляется **продажа здания целиком**.
Это отдельный пайплайн с другой аудиторией (инвесторы/покупатели, не арендаторы).
Таблицу новых лидов Дмитрий выгрузит отдельно.

## Правила работы (обязательные)

1. **Никаких записей в прод до бэкапа** (Фаза 0).
2. Перед любым пакетным изменением — **превью**: что меняется, у скольких строк,
   каких именно. Применять только после подтверждения Дмитрия.
3. Статусы и типы событий — строго из `CHECK constraint` в `src/lib/db/schema.sql`.
   Не выдумывать новые значения.
4. Работаем **пачками по сегментам**, не по одному лиду. Выдавать компактной
   таблицей, принимать решения голосом, применять группой.
5. Ответы и UI — по-русски (см. `CLAUDE.md`).

**Итог Фазы 0 (2026-09-01).** Бэкап `backups/2026-09-01-mitja-crm.sql` (61 КБ,
93/131/1/9/24/0 — сходится с фактами). `npm install` + `npm run build` — зелёные.

`.DS_Store`, `/backups` в `.gitignore` → 313 записей в `git status` стали 2.
Все страницы отвечают 200 (`/` → 307 на `/today`).

**Отдельная находка — exFAT ломает Turbopack.** `next dev` падал:
`Failed to open database → Loading persistence directory failed → invalid digit
found in string`. Это не база — libsql открывает `local.db` нормально.
Диск `/Volumes/SSD 2` отформатирован в **exFAT**, macOS заводит AppleDouble-файл
`._*` для каждого файла с расширенными атрибутами, а turbo-persistence парсит
имена файлов в своём хранилище как числа и спотыкается о них.

`rm -rf .next` — лечение симптома: файлы возвращаются при следующей записи кэша,
поэтому первый запуск проходит, а второй падает. Что ещё не сработало: симлинк
всего `.next` на внутренний диск — Turbopack начинает писать туда чанки, и оттуда
уже не резолвится `node_modules` проекта (500 на `@tailwindcss/postcss`).

**Рабочее решение:** увести на внутренний диск только `.next/dev/cache` —
персистентный кэш Turbopack, — оставив чанки в проекте:

    rm -rf .next && mkdir -p .next/dev
    mkdir -p ~/Library/Caches/mitja-crm-turbocache
    ln -s ~/Library/Caches/mitja-crm-turbocache .next/dev/cache

Проверено: переживает перезапуск, все страницы 200, `._*` внутри кэша — ноль.
Симлинк придётся пересоздавать после `rm -rf .next`. Настоящее лечение — вернуть
репо на внутренний диск (APFS); решать Дмитрию.

## Итог Фазы 1 — база разобрана полностью

**93 лида: 52 `dead`, 41 `replied_not_interested`, открытых 0, `next_action_due`
не проставлен никому.**

Главный вывод: восстанавливать было нечего. Гипотеза из шапки плана была в том,
что инструмент не звал обратно и поэтому работа встала. Разбор показал другое —
**работа встала потому, что старый пайплайн был выработан до конца.** Ни один из
93 лидов не дожил до сделки; все, с кем шёл диалог, либо отказались, либо
перестали отвечать. Пустая страница «Сегодня» была не багом, а честным ответом.

Поэтому `next_action_due` остаётся пустым, и это правильное состояние базы,
а не недоделка. «Сегодня» оживёт на новых лидах, не на этих.

**Что база даёт для следующей кампании — причины отказов повторяются:**

1. **Технические параметры здания.** Падель в кинозалах не строится (сегмент
   закрыт целиком, а не по лидам). «Невозможно разместить в кинозале» — дважды.
2. **Размер площадей.** «200 м² слишком мало», «нужно 2500 м²», «нужно от
   2000 м²». Наши 100–250 м² отсекают крупных операторов на входе.
3. **Рынок Пфорцхайма.** Кинооператоры: перенасыщено, второй зал не потянут.
   Церкви: «есть своё здание», «нет такой нужды».
4. **Деньги и таймлайн.** «Нет финансирования», «только открылись», «помещение
   на реконструкции» — интерес есть, ресурса нет.

Пункты 1–2 — про здание, их надо учесть в оффере до следующей рассылки, иначе
следующая сотня лидов отвалится по тем же причинам.

**Потери, зафиксированные при разборе:** Kletterarena обещали связаться «на
следующей неделе» и не получили ответа 99 дней; Fun Sport предлагали совместный

**Что в этих трёх пачках стоит внимания:** Fun Sport (id 24, лазертаг) —

## Инфраструктура и рабочее окружение (2026-09-02)

Не по плану, но заняло полдня и должно быть записано, чтобы не повторять.

**Переезд с внешнего диска на внутренний.** Проект лежал на `/Volumes/SSD 2`
(exFAT). macOS не умеет хранить там свои метаданные внутри файлов и плодит
файлы-двойники `._*`: 676 внутри `.git` (git падал с `non-monotonic index`),
2911 в `.next` (падал `next dev`), больше 25 000 в `node_modules`. Плюс диск
дважды отваливался посреди сессии. Переехали в `~/Websites/Project Mitja-CRM`:
скопировано без `node_modules` и `.next`, зависимости поставлены заново.
Показательно: `node_modules` весили **49 ГБ** на внешнем и **499 МБ** после
чистой установки. Файлов `._*` на внутреннем диске — ноль.
**Старая копия на внешнем диске не удалена** — удалить, когда убедимся.

**Переписанная история git.** Параллельная сессия вычистила из истории
`data/lumiera.csv` (95 строк персональных данных) и сделала force-push. Все хеши
сменились, обычный `git push` стал отвергаться. Разрешено переносом коммитов на
очищенную ветку (не слиянием — слияние втащило бы csv обратно). Конфликт в
`.gitignore` разрешён объединением обоих наборов правил. Точка возврата — ветка
`backup-2026-09-02`. Сам файл восстановлен на диск из неё: он нужен для работы,
но `/data` теперь заигнорен, в репозиторий не попадёт.

**Basic auth и Chrome.** Сайт отдаёт корректный `www-authenticate: Basic`, но
**Chrome не показывает окно ввода** — выводит голый текст «Authentication
required». В Safari диалог появляется нормально. Логин — `dmitry`, пароль хранится
только в переменных окружения Vercel (`BASIC_AUTH_PASS`), в репозитории его нет и
быть не должно. Менять: Vercel → Settings → Environment Variables → Edit, затем
**обязательно** Deployments → Redeploy, иначе новое значение не подхватится.
Для просмотра без пароля хватает `npm run dev` — middleware пропускает всех, если
переменные не заданы.

**Очистка папки.** Удалены пустые лог-файлы в `backups/` и кэш `.next` (314 МБ),
`Lumiera_Kaeuferliste_1.xlsx` перенесён в `data/` (там всё заигнорено). Дампы
прода в `backups/` оставлены — это страховка: 5 SQL-дампов и 3 копии `local.db`,
суммарно 1.2 МБ.

**Чем закончился день.** Код на GitHub (`3c7910b`), Vercel задеплоил, сайт
открывается. Прод: 170 лидов, 6 доп. контактов, 87 карточек с выжимкой из почты.
